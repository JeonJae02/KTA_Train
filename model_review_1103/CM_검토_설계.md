# 실무자 조치 vs 모델 경고 — Confusion Matrix 검토 설계

> 작성 2026-11-11 · 검토 기간 2026-10-16 ~ 11-10 · 대상 2라인
> 이 문서는 [`모델검토_계획.md`](모델검토_계획.md)의 4-2(예측 vs 조치)와 4-3(조치 영향)을 실제 작업 단위로 구체화한 것이다.
> 모델 동작 설명은 [`모델_알고리즘_정리.md`](모델_알고리즘_정리.md)를 본다.

## 1. 무엇을 하나

실무자가 현장에서 확인하고 조치한 기록을 "실제로 이상이 있었다"의 기준으로 삼는다. 그리고 그때 우리 모델이 경고를 냈는지 데이터로 확인한다.

확인하는 것은 세 가지다.

1. **맞춤(TP)** — 조치 전에 같은 설비에 경고가 떴는가. 그 경고의 피처 변화 시점이 조치 시점과 맞는가.
2. **놓침(FN)** — 실무자가 조치했는데 우리는 경고하지 않은 것. **어떤 피처를 봤어야 했는지**까지 찾는다.
3. **조치 없는 경고(FP 후보)** — 우리는 경고했는데 현장 조치가 없는 것. 현장이 놓친 것인지 모델이 과민한 것인지 가른다. 현장이 놓쳤을 법한 것은 현장 확인을 요청하고, 실제 이상이 확인되면 TP로 옮긴다.

모든 판정에서 같이 기록하는 것이 있다. **경고가 말한 내용**(사유·문구)과 **현장이 받아들이고 실제로 고친 것** 사이의 차이다.

결과는 혼동행렬 숫자로 정리한다. 이 숫자와 경고 시점(선행 시간)을 바탕으로, 나중에 "경고대로 움직였다면 공장이 얻었을 이익"을 계산한다. 그래서 그 계산에 필요한 값(선행 시간, 생산 영향, 작업 시간)도 지금 같이 남긴다.

## 2. 정의

### 2-1. 판정 단위

| 쪽 | 단위 | 만드는 곳 |
|---|---|---|
| 실제 (일지) | **사건** `incident_id` — 공무반·기계실 일지가 같은 일을 따로 적은 경우 하나로 묶는다 | `warning/actions/action_map.csv` |
| 예측 (경고) | **경고 에피소드** `episode_id` — 같은 대상의 경고가 뜬 순간부터 내려갈 때까지 | `warning/episodes/warning_episodes.csv` |

### 2-2. 혼동행렬

|  | 경고 있음 | 경고 없음 |
|---|---|---|
| **조치 있음** | TP — 사건 기준으로 센다 | FN — 사건 기준으로 센다 |
| **조치 없음** | FP — 경고 기준으로 센다 (현장 확인 후 확정) | TN — 설비 × 운영일 기준으로 센다 (나중에) |

단위가 섞이므로 지표를 이렇게 정의한다.

- **재현율** = TP(사건) / (TP(사건) + FN). 실무자가 손댄 것 중 우리가 미리 본 비율이다.
- **정밀도** = TP(경고) / (TP(경고) + FP). 우리 경고 중 실제 이상으로 이어진 비율이다. 사건 하나에 경고가 여러 건 붙을 수 있으므로 경고 기준으로 따로 센다.
- **TN**은 지금 세지 않는다. 오경보율과 이익 계산에 필요해지면 설비 × 운영일 단위로 센다.

표본이 몇십 건이다. 비율보다 **사례 목록**을 먼저 본다.

### 2-3. 짝짓기 규칙 (초안 — 회의에서 확정)

- **같은 설비키**이고, **조치 시작 전 7일 안에** 떠 있던 경고가 사전 탐지 후보(`phase=before`)다.
- 조치 후 24시간 안에 처음 뜬 경고는 '사후'(`phase=after`)로 따로 본다. 재가동 과도 상태이거나 조치가 효과 없었을 수 있다.
- 조치 시각은 일지의 작업일 + 기록시간 시작이다. 기록시간이 없으면 작업일 0시로 두고 `start_known=False`로 표시한다.
- 후보는 코드가 기계적으로 뽑는다. TP/FN/FP 판정은 **사람이 데이터를 보고** 라벨 파일에 적는다.

### 2-4. 피처 시점 일치

TP로 적으려면 경고가 떴다는 것만으로는 부족하다. **우리 모델이 쓰는 피처가 조치 시점 전후로 움직였는지** 확인한다.

- 조치 전에 이상 방향으로 벗어나 있었는가 (경고 근거)
- 조치 뒤 기준선 쪽으로 돌아왔는가 (조치 효과 + 피처 유효성)
- 돌아오지 않았다면, 경고가 다른 원인을 가리킨 것일 수 있다 (`meaning_gap`에 적는다)

조치 후 경고가 꺼지기까지 걸리는 시간은 모델마다 다르다. 펌프는 10사이클, 컨베이어 코어는 20회 통과, 유닛은 반나절~다음 날이다. 알고리즘 문서 5-1 표를 기준으로 판단한다.

### 4-2. 모델 경고 — `warning_episodes.csv`

엣지 경고 로그 `warnings.jsonl*`를 정리한 것이다.

- **(kind, key, time) 하나가 경고 한 건이다.** `time`은 처음 뜬 시각이고, updated 이벤트 내내 바뀌지 않는다.
- **한 건 안에서 사유가 바뀔 수 있다.** 펌프 진단이 바뀌는 경우로, 331건 중 31건이다. 그래서 `reason_first`와 `reasons`(전체 목록)를 둘 다 남긴다.
- `warnings.jsonl`(확장자 없음)은 날짜 파일과 줄이 겹친다. 완전히 같은 줄 242개를 지웠다.
- **시각은 전부 KST로 바꿨다.** 원본 로그는 UTC다.
- **짝짓기에는 `onset`과 `last_detected`를 쓴다.** `cleared`는 근무 구간 끝에 몰려 있어 실제 해소 시각이 아니다.
- 컨베이어 경고는 등급 2·3만 로그에 남는다(`max_sev`). 펌프는 `max_level`(주의/알림)이다.

**모델별 경고 로그 시작 시각.** 이보다 이른 조치는 경고 이력으로 판정할 수 없다. 라벨을 `PRE`로 두고 재생으로만 본다.

| 모델 | 첫 경고 (KST) | 검토 기간 경고 건수 | 해당 노트북 |
|---|---|---|---|
| 펌프 14대 | 10-15 18:58 | 161 | pump_check |
| 헤드 인젝션 (릴레이) | 10-19 06:50 | 28 | pump_check |
| 탱크 (릴레이) | 10-19 06:50 | 15 | etc_check |
| 컨베이어 | **10-26 06:19** | 127 | con_check |

**모델 버전 — 11-06 17:25 KST에 컨베이어가 v2.2로 바뀌었다.** 경고 로그 형식이 바뀐 시각이다.

| | v2.1 (~ 11-06 17:25) | v2.2 (11-06 17:25 ~) |
|---|---|---|
| 컨베이어 경고 키 | 유닛 하나에 지표 전부 (`md_fwd`, `airbag`, `drive`) | 부위 단위 — 실린더 SOL 주소(`P00470`, `P0028A`), 주소 없는 부위는 `CONVEYOR_MD_FWD:slide_sensor`, `CONVEYOR:drive` |

- `warning_episodes.csv`는 두 버전 경고를 같은 부위 체계로 읽는다(`model_ver`, `part_device`, `part_group` 열). v2.1 유닛 경고는 사유의 지표 이름으로 부위를 매긴다.
- **컨베이어 가동일 기록은 10-20 ~ 10-25가 비어 있다.** 씨앗이 10-19까지이고, 실시간 누적은 10-26부터다. 그 사이에는 모델이 돌지 않았다. 이 공백 때문에 10-26에 이미 해소된 상태가 이어받아진 사례가 있다(C01의 W0073).

### 4-3. 원시 데이터와 재생 — 피처 확인

경고 로그에는 상태 변화만 남는다. 피처가 언제 얼마나 움직였는지는 DB에서 원시값을 뽑아 운영 모델에 다시 흘려야 보인다.

- **추출**: `db.fetch_range(start, end, db.model_tags("pump"), group="pump")`. 운영 모델이 읽는 태그만 하루 단위로 뽑아 `cache/raw/`에 저장한다. 펌프 하루치는 112태그, 약 17만 행, 1분, 3MB다. **현장 DB이므로** 넓은 구간을 한 번에 뽑지 않는다.
- **펌프 재생**: `replay.pump_cycles(raw, pumps=[...])`. 사이클마다 점수, 판정 모드, 피처 8개의 정규화 값(`zn_pump_resid` `zn_r_phys` `zn_t_self` `zn_decel_half_sec` `zn_release_half_sec` `zn_ft_cv` `zn_pt_std` `zn_P0`)이 나온다. 창 판정이 비지 않도록 보고 싶은 시각보다 반나절 이상 앞에서 시작한다.
- **컨베이어 재생**: `replay.conveyor_core(raw, history=…, units=("md_fwd", "md_rev"))`. 결과는 세 가지다.
  - 통과 하나 = 한 행인 표: 시각, 센서, 대차, 앞 끝 위치, 켜짐 길이, 재감지 수
  - 주기마다 모델 화면에 떴을 판정
  - 유닛 사이클 값
  `history`에는 가동일 기록 중 재생 시작일 전 날만 넘긴다. 재생 결과는 기록 파일과 맞는다(C01에서 검증). `replay.attach_wagon()`은 유닛 사이클에 대차 번호를 붙인다.
- **탱크 재생**은 아직 헬퍼가 없다. 방법은 etc 노트북 4절에 있다.

## 5. 작업 흐름

세 노트북은 같은 순서로 진행한다.

```
0. (한 번) ../venv/bin/python warning/build_inputs.py
1. 입력       사건 목록, 경고 목록, 타임라인 그림
2. 후보       사건별 시간창 안의 경고 · 짝 없는 사건(FN 후보) · 짝 없는 경고(FP 후보)
3. 원시 태그   사건 하나를 골라 조치 전후 2일+1일을 DB에서 뽑아 그린다
4. 재생 피처   그 구간을 모델에 흘려 피처가 언제 움직였는지 본다
5. 라벨       labels_incidents.csv · labels_episodes.csv 에 판정을 적는다
6. 집계       혼동행렬 숫자
```

### 5-1. 라벨 값

**`labels_incidents.csv`** — 사건 한 행

| 열 | 값 |
|---|---|
| cm | `TP` / `FN` / `OUT`(모델범위 밖 — 분모에서 빼고 확장 후보로) / `PRE`(그 모델 경고 로그 시작 전) / `HOLD` |
| matched_episodes | 짝지은 episode_id (`;`로 구분) |
| match_level | `부위`(경고 문구의 부위 = 실제 조치 부위) / `설비`(설비만 같음) / `불일치` |
| lead_h | 경고 onset → 조치 시작 (시간). 이익 계산에 쓴다 |
| feature_shift | 조치 전후로 움직인 피처의 이름·방향·크기 |
| shift_time_ok | 피처 변화 시점이 조치 시점과 맞는가 `Y` / `N` / `애매` |
| missed_feature | FN일 때 어떤 피처나 신호를 봤어야 했는가. 기존 피처가 문턱 아래에서 움직였는지, 새 신호가 필요한지 |
| meaning_gap | 경고가 말한 것과 현장이 받아들인 것·실제 원인의 차이 |
| reviewer · note | |

**`labels_episodes.csv`** — 경고 한 행

| 열 | 값 |
|---|---|
| cm | `TP`(사건과 짝) / `FP` / `FIELD_CHECK`(현장 확인 요청 중) / `HOLD` |
| matched_incident | 짝지은 incident_id |
| fp_cause | `현장놓침의심` / `모델과민` / `재가동과도` / `데이터결측` / `진단오류`(이상은 맞는데 부위가 틀림) / `기타` |
| evidence | 판단 근거 — 피처 값, 그림 파일명 |
| field_check_req · field_check_result | 현장에 확인을 요청한 내용과 회신. 이상이 있었다는 회신이면 `cm`을 `TP`로 바꾼다 |

### 5-2. 조치 없는 경고를 가르는 순서

1. **데이터 문제인가.** 재가동 직후의 과도 상태, 수집 공백, 판정 범위 밖 사이클이면 `재가동과도` / `데이터결측`으로 적는다.
2. **피처가 실제로 벗어났는가.** 학습 때 날짜 간 흔들림 정도라면 `모델과민`이다. 문턱이나 창 크기 조정 후보가 된다.
3. **피처가 뚜렷하게, 오래 벗어났는가.** 그렇다면 `현장놓침의심` → `FIELD_CHECK`로 현장 확인을 요청한다.
4. 현장 회신으로 이상이 확인되면 `TP`, 이상이 없으면 `FP`로 확정한다.

### 5-3. 예시 — 확인 전 관찰

P01(10-19 06:00, 1-2 POL 펌프 "압력 안 걸림" → 펌프 교체)에 대해 우리 경고는 P2·I2 **"헤드 토출 저항 증가 · 압력 상승"**이었다. 10-15부터 떠 있었다. 현장은 "압력이 안 걸린다"고 보고 펌프를 교체했다.

- I2 쪽 경고는 교체 직후(마지막 감지 10-19 06:51)에 멈췄다. P2 쪽은 10-23까지 이어졌다.
- 10-19 재생에서도 교체 뒤 P2의 `zn_P0`·`zn_r_phys`는 높은 채(~1.0)로 남아 있었다.

경고가 가리킨 방향(압력↑)과 현장 증상(압력↓)이 반대다. `meaning_gap`에 기록할 전형적인 사례다. 교체 전 구간(10-17 이전)을 뽑아 비교해야 판정할 수 있다.

## 6. 협업 규칙

- **분담은 노트북 단위로 한다.** `con_check`, `pump_check`, `etc_check` 담당을 정한다. `review_lib/`를 고치면 세 노트북에 모두 영향을 주므로 커밋 메시지에 적는다.
- **판정은 라벨 CSV에만 적는다.** 노트북 출력은 근거일 뿐이다. 그림은 `figs/<incident_id>_*.png`로 저장하고, 그 파일명을 `evidence`에 적는다.
- 노트북 5절은 새 행만 추가하고 **이미 적은 라벨은 지우지 않는다**. 사라진 사건이나 경고는 `orphan=Y`로 남으니, 확인하고 사람이 지운다.
- **`action_map.csv`를 고쳤으면** `build_inputs.py`를 다시 돌리고 커밋한다. 새 일지가 들어와 `filtering.xlsx`가 바뀌어도 같다. 매핑이 없는 작업ID가 있으면 스크립트가 알려 준다.
- CSV는 엑셀 호환을 위해 `utf-8-sig`로 저장한다. 엑셀에서 저장할 때도 **CSV UTF-8** 형식을 고른다.
- `backend/`는 운영 코드 그대로 둔다. 운영 모델 동작을 바꿔 보고 싶으면 `review_lib`에서 상속하거나 감싼다.
- 파이썬은 `DB_Log/venv`를 쓴다. VS Code 노트북 커널도 이걸로 고른다. DB 접속 정보는 `DB_Log/.env`에 있다.
