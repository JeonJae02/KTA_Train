# 탱크 실시간 진단 흐름 정리

코드: `parkkt/Tank_Realtime_Model.py`
배치용 원본 규칙: `parkkt/Tank_Diagnosis_Model.py`, 전처리: `parkkt/Tank_Preprocess.py`

## 1. 전체 구조

```
PLC 원시값 (매 tick)
   │
   ▼
TankRealtimeGroup.update(current_time, row)          ← 최상위. 반복문에서 이것만 호출
   │
   ├─ 탱크별 TankRealtime.update()                   ← 모델. 가동 여부와 무관하게 항상 판정
   │     ├─ 규칙 ① heat       : 오늘 min(PV − L_Set) < 0 ?
   │     ├─ 규칙 ② exchanger  : 사이클이 켜진 뒤 10분 넘게 안 꺼짐 ?
   │     └─ 규칙 ③ 성능저하    : cool 동반 사이클 10회 연속 ?
   │     → 이상이 생기면 new_events 로 이벤트 발생
   │
   └─ 가동 플래그(Auto_Running_PL) 확인 후 띄울지 결정
         → 띄운 경보는 다음 오전 6시까지 유지
         → {"relay_warning": {...}}
```

사용법 (`check_running.py` 와 같은 방식):

```python
mon = TankRealtimeGroup()                    # 반복문 밖에서 한 번
while True:
    row = {...}                              # {태그명: 원시 PLC 값}. 이번 tick 에 들어온 것만
    result = mon.update(current_time, row)   # {"relay_warning": {...}}
```

- 값은 원시 PLC 값 그대로 넣는다. `TK_Temp_*` 는 0.1℃ 단위라 안에서 10 으로 나눈다.
- 이번 tick 에 안 들어온 태그는 빼거나 None 으로 두면 마지막 값을 이어서 쓴다.
- 시각은 tz 없는 한국시간, tz 붙은 시각, epoch 초 모두 받는다.

## 2. 입력 태그 (탱크 1개 기준, P1 예시)

| 용도 | 태그 |
|---|---|
| exchanger | `워킹 Tank 1 BACK Exchanger SOL` |
| cool | `워킹 Tank 1 BACK Cooling SOL` |
| PV | `TK_Temp_PV_P1` |
| L_Set | `TK_Temp_L_Set_P1` |
| SV | `TK_Temp_SV_P1` |
| 가동 플래그 (공통 1개) | `Auto_Running_PL` |

탱크: P1~P5, I1~I3 (8개). 한글 태그는 탱크마다 공백 개수가 달라서 `Tank_Preprocess.TANKS` 에 적힌 그대로 써야 한다.

## 3. 규칙 ② ③ — exchanger 사이클

### 채터링 병합 (90초)

exchanger 는 PV 가 SV 근처를 오갈 때 0.5~3초짜리 ON/OFF 를 반복한다(켜질 때와 꺼질 때 둘 다).
꺼진 뒤 90초 안에 다시 켜지면 같은 사이클로 본다.

- 근거: 실측 OFF 길이가 0.5~55.7초(채터링) / 402초 이상(진짜 OFF)으로 완전히 갈린다.

### 상태 3개

```
OFF ──(켜짐)──▶ ON ──(꺼짐)──▶ 꺼짐대기 ──(90초 경과)──▶ OFF   [cycle_end = 실제 꺼진 시각]
                 ▲                │
                 └─(90초 안 켜짐)─┘  같은 사이클 계속
```

- **꺼짐대기 동안은 켜진 시간으로 세지 않는다.** 세면 8분 30초~10분에 정상 종료된 사이클이 대기 중에 10분을 넘겨 가짜 경보가 된다(실측 29건).
- 90초 안에 다시 켜지면 `now − cycle_start` 로 이어서 센다. 꺼져 있던 틈도 포함하며, 배치의 `on_duration_sec` 와 같은 정의다.
- 90초가 지나면 `cycle_end` 를 90초 뒤가 아니라 **실제 꺼진 시각**으로 기록한다.

### 90초 대기가 경보를 늦추지 않는 이유

경보 조건이 "10분 넘게 켜져 있음" 이라서, **켜져 있는 도중** `cycle_start + 10분` 이 되는 순간 바로 뜬다.
90초 대기는 "정상 종료 확정"에만 걸린다.

- 유일한 지연은 "10분 전에 꺼졌다가 10분 넘어서 다시 켜진" 경우다. 다시 켜지는 순간에야 알 수 있는 정보라 어떤 방법으로도 줄일 수 없다.
- 실측: 10분 초과 126건 중 9건, 대부분 0.2~16초, 최대 80초(I2).
- 끝부분에도 채터링이 있어서(P2·I2 는 마지막 ON 조각 중앙값 0.5초) 대기 자체를 없앨 수는 없다.

### 판정

- **규칙 ②**: 켜진 뒤 `MAX_ON_SEC`(600초) 를 넘기면 이상.
  - cool 이 같이 안 켜졌으면 → exchanger ID
  - cool 이 같이 켜졌으면 → exchanger ID + cooler ID
- **규칙 ③**: 진행 중 사이클까지 쳐서 cool 동반이 `CONSEC_COOL_N`(10회) 연속이면 → exchanger 성능저하.
- cool 동반 여부는 `cycle_start ~ 마지막 꺼짐` 구간만 본다. 꺼짐대기 중 켜진 cool 은 다시 켜지면 합치고, 사이클이 확정되면 버린다.
- 켜진 도중부터 보기 시작한 사이클(재시작 직후)은 첫 샘플 시각부터 센다. 실제 길이는 그보다 길 수밖에 없으니 10분을 넘으면 이상으로 봐도 틀리지 않는다. 배치는 이 사이클을 버린다.

## 4. 규칙 ① — heat (일별 최저 PV)

- 하루치를 모으지 않고 **`min(PV − 그 순간의 L_Set)` 를 변수 하나로 갱신**한다.
  - 메모리 문제라기보다(하루치를 다 들고 있어도 탱크당 약 0.85MB) 재계산·재시작 복구가 단순해진다.
  - L_Set 은 일별 중앙값 대신 그 순간의 값과 비교한다. 하루 중간에 바뀌어도 맞게 판정된다.
- **하루 경계는 한국시간 오전 6시.** 06:00 전은 전날로 친다.
- **6시 초기화 때 최저 PV 는 SV 에서 시작한다.** 전날 최저값이 SV 보다 낮게 남아 있어도 SV 로 올려서 새로 센다.
  - SV 를 아직 모르면(시작 직후) 첫 SV 가 들어올 때 채운다.
  - 전날 요약은 `last_day` 에 남긴다.
- **글리치(허용범위 5~60℃ 밖 PV)는 최저값에 절대 넣지 않는다.** 한 번 들어가면 그날 하루가 통째로 오판정되고 되돌릴 수 없다(실측 0℃ / 327℃ 기록 있음).
- PV 가 L_Set 밑으로 내려가는 순간 그날 판정이 확정되므로 다음날까지 기다리지 않고 바로 경보를 낸다.
  - `HEAT_CONFIRM_SEC`(기본 0)를 올리면 그 시간만큼 이어져야 인정한다. 범위 안에서 한 샘플만 튀는 경우 대비용이다.

## 5. 이벤트와 가동 플래그

### 모델은 이벤트만 낸다

같은 이상은 한 번만 낸다.

- exchanger / cooler / 성능저하 → **사이클당 한 번**
- heater → **PV < L_Set 구간당 한 번** (6시에 새로 센다)

하루에 한 번이 아니라 이 단위로 내는 이유: 아침 예열 때 막힌 경보 때문에 같은 날 가동 중에 생긴 진짜 경보까지 묻히는 걸 막으려는 것이다.

### 최상위가 띄울지 결정한다

이벤트가 난 **그 순간** `Auto_Running_PL` 이 1 일 때만 띄운다.

| 사유 | 비가동 중 |
|---|---|
| exchanger / cooler / 성능저하 | 안 띄움 (`suppressed` 에 기록) |
| heater | **항상 띄움** — L_Set 밑으로 가는 건 가동과 무관하게 이상 |

- 플래그를 한 번도 못 받았으면 가동 중으로 보고 띄운다. 태그가 빠졌을 때 경보가 조용히 사라지는 것보다 낫다.
- 플래그는 원래 값 그대로 쓴다(120초 유지 처리 없음).
  - 자동운전 시작 순간 1~2초 깜빡임이 하루 2개 정도 있다.
  - 유지 처리를 넣어도 결과가 거의 같았다(이상 24건 vs 23건).
- 띄운 경보는 다음 오전 6시까지 유지한다.

### 왜 가동 플래그가 필요한가

실측(9/9~10/6, 8탱크)에서 10분 초과 126건 중 **103건이 비가동 중 시작**했다. 그중 97건이 05~06시로, 생산 시작(06:50) 전 예열 구간이다. 8개 탱크가 동시에 걸린 경우도 있다.

| 사이클 시작 시점 | 10분 초과 비율 |
|---|---|
| 비가동 | 3.88% |
| 가동 | 0.15% |

### 가동 판정 신호 비교

| 신호 | 남는 이상 | 비고 |
|---|---|---|
| **`Auto_Running_PL`** | 24 | **채택.** 태그 1개, 생산 시작 시각(06:50, 09:00, 11:30 …)과 정확히 일치 |
| 인젝션 + P0025D (check_running 수정판) | 23 | 태그 5개 필요 |
| `Conv_Run_PL` / `CONVEYOR RUN / STOP PL_HMI` / `P0025D` | 44~45 | 셋이 99.6% 이상 같은 신호. 컨베이어가 06:24 에 먼저 돌아 예열 구간을 못 거름 |

참고 — `check_running.py` 원본은 시작 조건이 "Injection_On 120초 연속" 인데, 인젝션 비트는 펄스(중앙값 1.1초)라 사실상 가동으로 안 넘어간다(가동 비율 0.3%).

| 이름 | 값 | 위치 |

## 7. 검증

- **P1 일주일(9/14~9/20) 재생 vs 배치**
  - 사이클 443개의 시작·끝·cool 동반이 모두 일치했다.
  - 10분 초과는 6 / 6 으로 같았다.
  - 6시 기준 일별 최저 PV 가 7일 모두 일치했다.
  - 처리 속도는 한 샘플에 약 5µs.
- **8탱크(9/9~10/6) 재생, 가동 플래그 적용**
  - 띄운 exchanger 경보 28건, 비가동이라 막은 경보 104건.
  - 05~06시 경보는 0건.
  - 탱크별: I2 14, P5 6, I3·P1·P2 각 2, I1·P3 각 1.
- **시나리오 테스트 통과**
  - 예열 중 이상은 막힌다.
  - 같은 날 가동 중 이상은 뜬다.
  - 6시에 초기화된다.
  - heater 는 비가동이어도 뜬다.
  - 플래그가 없으면 띄운다.
  - SV 시작값 동작도 확인했다.

## 8. 남은 것

- **I2 `MAX_ON_SEC` 900초:** 가동 중 I2 ON 길이는 99% 이내 682초, 최대 824초다. 900초로 올리면 가동 중 I2 이상이 0건이 된다. 아직 적용하지 않았다.
- **진짜 이상으로 보이는 건:** P1 2997초, I3 3124초. P5·P2 의 10~12분짜리는 경계선이다.
